# CERT Insider Threat Test Dataset (r4.2): data preparation

This project uses the **CERT Insider Threat Test Dataset** as its primary external benchmark, plus a *separate* synthetic
supplement for gaps and controlled test cases.

> **The CERT collection is synthetic.** It was generated by the CERT Division of Carnegie Mellon University's Software
> Engineering Institute with ExactData, LLC (DARPA I2O): synthetic background users plus synthetic malicious actors.
> It is **not real banking data**, and nothing computed from it describes a real organisation. The same statement is
> printed in `dataset_report.json`, the SOC dashboard and `/api/detection/status`.

* Official page: <https://sei.cmu.edu/library/insider-threat-test-dataset/>
* Download (DOI): <https://doi.org/10.1184/R1/12841247.v1> (Carnegie Mellon KiltHub, version 1, 2020-09-30), licence **CC BY 4.0**
* Reference paper: *Bridging the Gap: A Pragmatic Approach to Generating Insider Threat Data* (linked from the official page)
* Not used: the Hugging Face mirror (`nguynn/cert-insider-threat-datasets`). It is gated behind a login and a terms
  acceptance, so it was not inspected; the official source was reachable and is what the checksums below refer to.

## Which release, and why r4.2

The official page says each dataset archive contains its own readme and that later releases are supersets of earlier
ones. The KiltHub record lists r1, r2, r3.1, r3.2, r4.1, r4.2, r5.1, r5.2, r6.1, r6.2 and `answers.tar.bz2`.
**r4.2** was chosen because, after reading its readme and the answer key:

* it has every event source the pipeline uses: `logon`, `device` (removable media), `http`, `email`, `file` (copies to removable media), plus LDAP organisational snapshots;
* the answer key lists the *individual malicious events by their original event id* (70 incident files), so labels can be joined event by event instead of "all events of a malicious user";
* it is a "dense needles" release with many instances of scenarios 1, 2 and 3, which gives enough positives to evaluate on;
* its columns are simpler than later releases.

Trade-off, stated plainly: "dense needles" means malicious activity is unrealistically common. Prevalence, precision and
anything derived from them must not be extrapolated to a real organisation.

| Scenario in r4.2 | Insiders | Description (answer key `scenarios.txt`) |
|---|---|---|
| 1 | 30 | Starts logging in after hours, using a removable drive and uploading data to wikileaks.org, then leaves |
| 2 | 30 | Job-site browsing and soliciting a competitor, then markedly higher thumb-drive use before leaving |
| 3 | 10 | System administrator installs a keylogger via thumb drive on the supervisor's machine, logs in as the supervisor and sends an alarming mass e-mail |

Scenarios 4 and 5 exist only in other releases.

## Get the data (user action required)

Nothing here downloads data for you, and the data is never committed (`data/external/`, `data/processed/` and
`*.tar.bz2` are git-ignored). Everything is processed locally; do not upload it to a public deployment or an external service.

1. Download from the DOI page above: `r4.2.tar.bz2` (4,824,287,500 bytes), `answers.tar.bz2` (1,254,678 bytes) and `CHECKSUMS-sha256.txt`. (The KiltHub API at `https://api.figshare.com/v2/articles/12841247` lists the direct file links; the server supports HTTP range requests, which helps on slow connections.)
2. Verify the checksums (these are the official values):

   ```powershell
   Get-FileHash r4.2.tar.bz2 -Algorithm SHA256       # 586446b00e83ce5cdabf9dc889b0b6e7a9f44556cee3c03d39445d790122556c
   Get-FileHash answers.tar.bz2 -Algorithm SHA256    # ed21bf921def01e97326b314f2d1fa77651a945bd31bf513095f8ac7658c9ddd
   ```
3. Put them in `data/external/cert/` and extract (about 15 GB; `http.csv` alone is 13.9 GB):

   ```powershell
   python -m ml.cert.prepare --extract data/external/cert/r4.2.tar.bz2          # or: tar -xjf r4.2.tar.bz2
   mkdir data/external/cert/answers-extract; tar -xjf data/external/cert/answers.tar.bz2 -C data/external/cert/answers-extract
   ```

Expected layout:

```
data/external/cert/
  r4.2.tar.bz2  answers.tar.bz2  CHECKSUMS-sha256.txt
  r4.2/            logon.csv device.csv http.csv email.csv file.csv psychometric.csv readme.txt license.txt LDAP/YYYY-MM.csv
  answers-extract/answers/   insiders.csv scenarios.txt readme.txt r4.2-1/ r4.2-2/ r4.2-3/ (one observables file per incident)
```

## Validate, prepare, supplement

```powershell
python -m ml.cert.validate --source data/external/cert/r4.2 --answers data/external/cert/answers-extract/answers
python -m ml.cert.prepare  --source data/external/cert/r4.2 --answers data/external/cert/answers-extract/answers --out data/processed/cert_r4.2
python -m ml.cert.synthetic --out data/processed/synthetic_test --seed 42 --profile data/processed/cert_r4.2/cert_profile.json
```

* `validate` only reads: it checks files, columns, timestamp format, duplicate ids and the answer key, and prints actionable errors (missing file, missing columns, header-only or unreadable files, wrong release, truncated archive).
* `prepare` never writes into the dataset directory (it refuses an `--out` inside it) and replaces only its own derived files. Options: `--sources logon device ...`, `--sample-users N` (all insiders kept; prevalence then unrepresentative, flagged in the report), `--hash-sources` (SHA-256 of each source file in `manifest.json`), `--seed`. The full run takes about 45 minutes, almost all of it `http.csv` (28.4 million rows).
* Tests: `python -m pytest tests/test_cert_dataset.py -q`. They build a miniature release in CERT's layout and need no download.

## Outputs and what each one is for

| File | Contains | Use |
|---|---|---|
| `events_<source>.csv.gz` | canonical events, **no labels**, pseudonymous `entity_id` | training features, dashboard display |
| `labels.csv` | explicit ground truth: `event_id, label, label_basis` (listed events only; absence = benign) | evaluation only |
| `eval_metadata.csv` | scenario, insider user, incident file, incident window per listed event | evaluation only |
| `splits.csv` | `entity_id -> train / validation / test`, `is_insider` | partitioning, evaluation |
| `identity_map.csv` | `entity_id -> CERT user id` | display / evaluation only |
| `entity_attributes.csv` | role, business unit, functional unit, department, team from the latest LDAP snapshot | optional context (see caveat) |
| `cert_profile.json` | hour-of-day and per-user-day behaviour of **benign events of train users** | drives the synthetic supplement |
| `dataset_report.json`, `manifest.json` | counts, rejects, duplicates, label coverage, caveats; parameters, source file sizes and SHA-256 | audit trail |

## Field mapping (source -> canonical)

Canonical columns: `event_id, source, timestamp_utc, entity_id, host, event_type, activity, auth_result, destination,
resource, bytes, attachment_count, recipient_count, external_recipient_count, removable_media, is_synthetic`.
A value the source does not contain is left **empty / NaN**, never invented. The column layouts below were verified
against the extracted release (headers read directly from the files).

| Source file (columns read) | Canonical result |
|---|---|
| `logon.csv` (id, date, user, pc, activity) | `event_type` `logon` / `logoff` from Logon/Logoff; `activity` the lower-cased raw value; `host` = pc. No `auth_result`: the file has no failures |
| `device.csv` (id, date, user, pc, activity) | `device_connect` / `device_disconnect`; `removable_media = true` |
| `http.csv` (id, date, user, pc, url) | `web_visit`; `destination` = `resource` = host name of the URL (lower-case, `www.` removed). Path, query and the `content` column are discarded |
| `email.csv` (id, date, user, pc, to, cc, bcc, from, size, attachments) | `email_send` (the row's user is the sender); `recipient_count` = addresses in to+cc+bcc; `external_recipient_count` = those whose domain is not the organisation's (`dtaa.com`, detected as the most common sender domain); `destination` = distinct recipient domains; `bytes` = `size` (message size excluding attachments, per the readme); `attachment_count` = `attachments`. Subject/body `content` is discarded |
| `file.csv` (id, date, user, pc, filename) | `file_copy_removable`; `resource` = file name; `removable_media = true`. The release readme says every entry is *a file copy to a removable media device*, so this is **not** general file access. No size exists: `bytes` stays empty |
| `LDAP/*.csv` | role, business unit, functional unit, department, team only. Names, e-mail addresses, supervisors and `psychometric.csv` scores are never copied |

Other fields:

* **Not available in r4.2, so not produced:** source IP addresses (only `host`, the PC id), authentication success/failure, file sizes, transferred bytes for http and files, web content categories.
* **Host instead of IP.** The application's "unfamiliar IP" notion has no counterpart; a later "unfamiliar host" feature must be built from `host` and documented as such.
* **`user` -> `entity_id`:** `E` + first 12 hex digits of SHA-256 of `cert_r4.2:<user>`. Deterministic, so reruns agree; the real id is only in `identity_map.csv`.
* **Time zone.** CERT timestamps (`MM/DD/YYYY HH:MM:SS`) have no UTC offset. They are the organisation's local clock and are stored unchanged, labelled `+00:00`. "Hour of day" therefore means organisation-local hour; do not convert them again.
* **Rejected rows** (counted in the report, never silently dropped): missing id/date/user, unparseable timestamp, unknown activity value. **Duplicates** (same event id, within or across read chunks, hash-checked) are dropped and counted.
* **Release quirks** (from the readme): screen unlocks are recorded as logons, a few daily logons are intentionally missing, some device connects lack a disconnect, users may log on to another user's PC.

## Labels

The answer key lists, for every incident, the exact observable events (`type, {event id}, date, user, pc, ...`).

| Label | Rule |
|---|---|
| `1` malicious (`answer_key_event`) | the event id is listed **and** the event is recorded under the insider's own account |
| missing (`answer_key_other_account`) | listed, but recorded under another account (scenario 3). Genuinely ambiguous: excluded from supervised metrics |
| `0` benign (`no_answer_key_entry`) | not listed. Benign **by convention only**: the key cannot prove that an insider's unlisted event was innocent |

Events from a malicious user that are not listed are *not* labelled malicious. The report counts labelled events that
fall outside their incident's start/end time (`malicious_events_outside_incident_window`). Because of the ambiguity and the
absence-means-benign convention, any metric computed from these labels must say so; the report does not call the labels complete.

## Splits and leakage prevention

* **Users, not events, are split** (seeded, stratified so insiders are spread proportionally): train 55 %, validation 15 %, test 30 %. No person appears on both sides.
* An unsupervised model should be fitted on **benign events of train users only**; validation tunes thresholds; test users are touched once.
* **Four separate stores:** training features (`events_*`), ground truth (`labels.csv`), evaluation metadata (`eval_metadata.csv`, `splits.csv`), display fields (`identity_map.csv`, `entity_attributes.csv`).
* `ml/cert/leakage.py` enforces it: `MODEL_INPUT_COLUMNS` is the only event-level view a detector may read (`model_input_view`); `assert_no_leakage(columns)` rejects label, scenario, answer-key, incident, user/entity id, split, source and `is_synthetic` columns and suspicious names; `history_before(events, as_of)` returns strictly earlier events so a feature can never use the event being scored or the future; `assert_disjoint_users` and `assert_cert_only` guard the split and keep synthetic events out of CERT evaluation.
* `entity_id` is a grouping key only. **Role caveat:** every scenario-3 insider is a system administrator in r4.2, so `role` from LDAP is informative about the answer key. It is kept out of `MODEL_INPUT_COLUMNS`; if used, say so.
* `cert_profile.json` is computed from benign events of **train** users only, so the synthetic supplement does not leak test users either.

## Synthetic supplement (`ml/cert/synthetic.py`)

A separate generator for what r4.2 cannot cover (failed authentication, volume-based bulk export, external transfer
sizes, gradual accumulation) and for controlled tests. It writes to its own directory, tags every row
`source = synthetic_test`, `is_synthetic = true`, uses IDs `SYN-nnnnnnn`, users `SYN-Uxxxx`, hosts `SYNPC-xxxx` and only
reserved `.example` / `.invalid` domains. **It is never added to CERT records or to the CERT test set.**

* **Reproducible:** `--seed 42` by default; `--random-seed` draws a fresh seed for interactive demos and records it in `manifest.json`.
* **Realism:** hour-of-day, web and e-mail volumes and e-mail size quantiles come from `cert_profile.json` (benign train users) when supplied; otherwise documented defaults. Server file-access volume uses defaults because r4.2 only has removable-media copies.
* **Threat scenarios (label 1 only on the injected events):** `gradual_data_collection`, `bulk_export`, `unusual_external_transfer`, `removable_media_exfiltration`, `account_misuse`, `multi_stage_sequence`.
* **Benign lookalikes (label 0):** `legit_large_transfer`, `approved_odd_hours`, `frequent_authorised_access`, `routine_removable_media`.
* **Noise:** optional fields randomly dropped (`missing_rate`, default 3 %), occasional benign failed logons, ordinary background activity for every user.
* `manifest.json` records the seed and mode, all parameters, event counts, per-scenario event/user counts, and the **reason each scenario was added**.

Reports must stay separate: CERT dataset-backed evaluation on the held-out CERT test users is one report; synthetic
scenario testing is another. Never combine the two numbers.

## Result of the full r4.2 run (measured)

Produced by `python -m ml.cert.prepare ... --hash-sources` on the official release (archive SHA-256 verified against the
official checksum file; 45.7 minutes, every row read):

| Source | Rows read | Rows written | Rejected | Duplicates |
|---|---|---|---|---|
| logon | 854,859 | 854,859 | 0 | 0 |
| device | 405,380 | 405,380 | 0 | 0 |
| http | 28,434,423 | 28,434,423 | 0 | 0 |
| email | 2,629,979 | 2,629,979 | 0 | 0 |
| file | 445,581 | 445,581 | 0 | 0 |

* 1,000 users (70 insiders), events from 2010-01-02 to 2011-05-17.
* Answer key: 70 incidents, **7,323 listed events, all 7,323 found in the data by event id**; 7,273 labelled malicious, 50 ambiguous (scenario 3, other accounts) and excluded from metrics; 0 labelled events outside their incident window. By scenario: 1 = 345 events (30 insiders), 2 = 6,765 (30), 3 = 213 (10, of which 50 ambiguous).
* User split: train 550 users (39 insiders), validation 150 (10), test 300 (21).
* The release needed no repair: no unparseable timestamps, missing fields, unknown activities or duplicate ids were found. The tests still exercise those paths with deliberately broken fixtures.
* Synthetic supplement generated with the CERT profile: 269,705 events (4,363 malicious), seed 42, no event-id overlap with CERT.

These are statistics about the *prepared data*. No detector has been evaluated on it yet.

## Limitations

* Synthetic data (see the notice above). "Dense needles" prevalence. Labels are partly ambiguous (scenario 3) and benign-by-absence.
* No IP address, authentication result or file/http volume in r4.2; the application's current feature set (which uses IPs and record counts) is **not** directly applicable to it, and a CERT-specific feature builder is a separate step.
* Timestamps carry no UTC offset.
* Only releases with this r4.2 layout are supported; other releases fail validation with a column-level message.
